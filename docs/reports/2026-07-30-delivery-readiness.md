# FoamPilot 交付成熟度评估

评估日期：2026-07-30
评估快照：基线提交 `1ecc5cf` 及本报告所在 revision
目标读者：公司管理层、仿真智能体产品负责人、CFD 技术负责人

## Executive Summary

- **当前可以有条件交付。** FoamPilot 已具备独立 Python 包、CLI、公开知识、受控执行、有限修复、严格评测和证据留存能力，适合作为同一台已配置工作站上的内部研发验证包或 Agent+CFD 技术基线。
- **核心求解闭环已经成立。** 已实际测试 28 个不同 TaskSpec，其中 15 个进入正式评测套件；15 题全部进入目标 OpenFOAM 求解器。仓库具有 222 项通过的自动化测试、36 条冻结知识、21 个 solver-family guide 和 4 个行为 Skill。
- **尚不能按跨机器产品交付。** 运行配置仍绑定 `/home/edwin`、本机 OpenFOAM-10 和个人 Codex OAuth 路径；仓库没有 CI、发布标签、锁定环境、企业凭据方案或干净机器安装证据。
- **物理证据仍需一次最终闭环。** 15 题冻结基线为 11/15，四个失败族后来分别修正并通过，但尚未用最终代码执行一次统一的全新 15 题复验，因此不能对外宣称稳定 15/15。
- **建议采用分级交付。** 先完成“可复现内部技术包”，再推进“可移植内部试点”，最后才考虑“外部产品交付”；不应把产品化工作混入当前轻量求解主流程。

## 交付前必须补齐的内容

### P0：形成可复现的内部技术交付包

1. **推送已验证提交。** 将本报告所在的已验证 revision 推送至远程仓库；`origin/main` 尚未包含本轮新增知识、运行可靠性修正和扩展场景复测报告。
2. **执行最终 15 题统一复验。** 使用最终提交和固定模型配置重新运行 `controlled-learning-15-v1`，不能用四个独立修正结果代替统一回归。
3. **保存轻量证据包。** 至少保留 suite JSON/Markdown 报告、每题 summary、manifest、关键日志摘要、wheel SHA256、模型名称和运行环境清单。大规模场结果可留在外部制品存储。
4. **建立版本化交付点。** 更新版本号，补充 CHANGELOG，创建可追溯 Git tag，并记录 wheel 哈希。
5. **完成干净环境安装验证。** 在新虚拟环境中从仓库或 wheel 安装，运行 preflight、自动化测试和至少一个真实算例。

完成这些动作后，可以正式定义为“FoamPilot 内部研发技术基线”。

### P0：跨机器或公司内部试点前的阻断项

1. **移除用户目录硬编码。** `RuntimeConfig.local_foundation_v10()` 和 sandbox 目前写死 `/home/edwin/workplace/OpenFOAM-10`、Python 路径及 `/home/edwin` 目录结构。应改为 CLI 参数、环境变量或配置文件，并提供自动发现与明确报错。
2. **建立企业级模型提供方边界。** 当前 CLI 默认读取 `~/.codex/auth.json` 并调用 Codex OAuth 后端。内部试点需要明确受支持的模型 API、服务账号、密钥管理、超时、限流、审计和费用归属。
3. **统一模型默认值。** `plan/solve` 默认模型与 `qualify` 默认模型不同，文档又显式使用另一固定值；交付版本必须冻结和记录默认模型策略。
4. **拆分可移植测试与主机集成测试。** 当前完整测试包含依赖本机 OpenFOAM 和 bubblewrap 权限的检查。CI 应分别运行纯 Python 测试、wheel 安装测试和具备 OpenFOAM 镜像/Runner 的集成测试。
5. **提供可复现环境。** 当前依赖只声明最低版本，没有 lock 文件或已验证的容器/环境清单。应冻结 Python 依赖，并记录 OpenFOAM、MPI、bubblewrap 和系统库版本。

这些问题不要求改变求解主流程，但决定仓库能否离开当前工作站。

### P1：产品化前需要补齐

1. **自然语言入口产品化。** 仓库原生入口仍是 YAML TaskSpec；当前由外部 Codex 将人的需求转为 TaskSpec。若产品承诺“直接自然语言求解”，需要把需求澄清、TaskSpec 生成和人工确认做成正式入口。
2. **评测资产再生能力。** 参考 JSON 有 source hash 和 tolerance provenance，但缺少面向交付方的 golden 生成/复核脚本和操作手册。
3. **安全审查。** 对模型输入、凭据读取、路径挂载、bubblewrap、MPI、公开资产和日志脱敏执行正式威胁建模和代码审查。
4. **依赖与许可证治理。** 增加依赖漏洞检查、许可证清单、SBOM，并由法务确认当前 `LICENSE` 版权主体、Foam-Agent 来源说明以及基于 OpenFOAM GPL 来源形成的知识条目如何对外交付。
5. **稳定 API 与兼容策略。** 明确 TaskSpec、ExecutionPlan、报告和 qualification suite 的版本升级规则。
6. **可观测性与成本基线。** 统计模型调用次数、token/费用、求解耗时、并行效率、失败层分布和产物占用。
7. **用户与运维文档。** 增加安装排障、凭据配置、资源规划、升级回滚和常见 solver-family 限制。

## 当前不应作为交付阻断项的内容

以下能力可以作为后续路线，而不应重新塞入当前主流程：

- MCP 注册；
- FAISS 或大型 RAG 数据库；
- 多智能体协同；
- 图形化前端；
- OpenFOAM-13/ESI 多版本兼容；
- Slurm/HPC 调度平台；
- 通用 CAD、Gmsh 或 snappyHexMesh 自动建模平台；
- 自动修改并晋升知识而无需人工审批。

只有当交付对象明确要求这些能力时，才应作为独立适配层建设。

## 建议采用三阶段交付

### 阶段一：内部技术基线

目标是让公司内部 CFD/Agent 研发人员在当前工作站上复现结果。

交付内容包括源代码、wheel、README/AGENTS、15 题套件、评测报告、manifest 和运行环境清单。完成远程推送、版本标签和最终统一 15 题复验后即可进入该阶段。

### 阶段二：可移植内部试点

目标是让另一位工程师在另一台受控机器上独立安装和运行。

必须完成配置解耦、企业模型凭据、依赖冻结、CI/集成测试和干净环境验收。验收标准应至少包括一个新机器的 15 题复现报告。

### 阶段三：外部或产品级交付

目标是进入客户试点或公司正式产品体系。

在阶段二基础上增加安全、法务、稳定 API、监控、成本、支持和版本生命周期。该阶段需要产品、平台、安全、法务和 CFD 专家共同签字。

## 建议汇报口径

可以向管理层表述为：

> 在人-Agent协作下，FoamPilot 已经完成从自然语言需求结构化为 TaskSpec，到 Agent 独立编写 OpenFOAM case、安全执行、日志驱动修复、物理评测和经验沉淀的核心技术闭环。当前已测试 28 个不同算例，其中 15 个构成正式评测套件；仓库拥有 222 项通过的自动化测试、36 条可审计知识和完整的运行证据机制。它已经可以作为公司 Agent+CFD 的内部技术基线，但尚未达到跨机器产品交付条件。下一阶段的重点不是重写求解架构，而是完成路径与凭据解耦、最终 15 题统一复验、CI/发布工程以及安全和法律治理。

不建议使用以下表述：

- “已经稳定通过全部 OpenFOAM 官方题库”；
- “可以解决任意 CFD 问题”；
- “已经达到生产级或客户交付标准”；
- “模型生成结果具有确定性”；
- “已经完成一次最终版本的 15/15 全量验证”。

## 需要管理层确认的问题

1. 第一阶段交付对象是当前开发者、公司内部 CFD 团队，还是另一台独立机器上的试点用户？
2. 公司允许使用哪一种模型服务和凭据管理方式？
3. 交付目标是技术基线、内部工具还是对外产品？
4. 谁负责 OpenFOAM 物理验收、评测 golden 审核和最终工程签字？
5. 是否需要把运行证据保存到公司制品库，以及保存哪些场文件和日志？

这些选择会改变交付工作量，但不要求改变 FoamPilot 当前的核心求解闭环。

## 证据边界与假设

- 本报告基于基线提交 `1ecc5cf`、本报告所在 revision 的仓库文档与测试，以及 2026-07-29 至 2026-07-30 的真实运行报告。
- 自动化测试通过不等于物理结果正确；solver 完成、公开验证和严格 qualification 是不同结论。

- 额外浅水算例通过公开验证，但没有作为永久严格评测夹具纳入 15 题套件。
- 法律与安全部分是工程风险提示，不构成法律或安全认证意见。
